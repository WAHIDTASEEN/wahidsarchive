# Security audit notes — 2026-10-28

## Changes made in this ZIP
- Added a first-entry sign-in gate to HTML pages (login page excluded). A session is checked against Supabase Auth; expired sessions are refreshed where possible. The original page URL is returned to after sign-in.
- Added a client-side limit of five password/OTP verification attempts in a rolling 60-second window, shared across those forms in this browser. This is a UX safeguard only: users can clear browser storage or bypass JavaScript. It is **not a substitute for server-side rate limiting**. Configure Supabase Auth rate limits in the Supabase dashboard or put auth behind a server-side rate limiter to enforce a strict IP/account limit.
- Added security response headers in `netlify.toml` and redirects denying common `.env` and `.git` paths.
- Kept the existing Supabase publishable/anon key in the frontend config. A publishable/anon key is designed to be public; it must be protected by correct Supabase Row Level Security (RLS) policies. Never place `service_role`, Resend, or other secret keys in browser JavaScript.

## Findings / items that cannot be verified from this ZIP
- The ZIP contains no `.git` directory/history, `.env` files, lockfile, or dependency manifest. Git-history secret scanning and dependency vulnerability auditing therefore cannot be completed from this archive.
- Netlify environment variables and Supabase dashboard settings are remote account settings and are not readable from this ZIP. Confirm `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `NEWSLETTER_ADMIN_USER_ID`, and `NEWSLETTER_FROM` are set in Netlify as applicable; keep secret values only in Netlify Functions environment variables. Rotate any secret ever committed or exposed.
- The front-end gate is not true static-file access control: HTML/JS/assets can still be fetched directly by URL. Do not place confidential files in the published directory. Private materials must be served through authenticated server-side endpoints or private Supabase Storage with RLS/signed URLs.
- **High-priority database finding:** the supplied `supabase.sql` includes `messages_owner_read` and `messages_owner_delete` policies with `using (true)` for all authenticated users, and `events_owner_read` also uses `using (true)`. This can let any authenticated account read contact messages/events and delete messages. I did not silently replace these with a guessed admin UID/role because the intended admin identity/claim is not included in the ZIP. Before deploying, replace these policies with an explicit administrator-only check (for example, a verified `app_metadata.role = 'admin'` claim or a fixed admin UID) and test with both admin and ordinary-user accounts.
- Admin authorization depends on Supabase RLS and policies; the browser code alone cannot prove that only an administrator can write `works`, `site_settings`, or storage objects. Verify every relevant table and storage bucket has RLS enabled and write policies restricted to the intended admin UID/role. Do not assume any authenticated user is an administrator.
- Password hashing is managed by Supabase Auth; this static site does not store password hashes itself. Review Supabase Auth settings, MFA, password policy, email confirmation, session lifetime, and Auth rate limits.
- Netlify Functions in this ZIP use service-role credentials. Keep those keys only in Netlify environment variables. The newsletter subscription endpoint is public and does not include durable per-IP rate limiting; add a managed rate limiter or a database-backed limit before relying on it against abuse.
- The security headers were kept compatible with the site's existing inline scripts and third-party CDN usage. A strict full Content Security Policy with nonces/hashes requires refactoring existing inline scripts and auditing all external origins.

## Validation status
This is a static source review and patch, not a penetration test. Deploy to a staging site first, verify login/session refresh, deep-link redirects, admin operations, newsletter flows, and all tools. Then inspect live response headers, Supabase RLS policies, Netlify environment variables, and Git history before describing the deployed site as fully secured.
